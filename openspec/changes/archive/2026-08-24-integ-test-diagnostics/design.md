## Context

`integration-tests.sh` runs the `systest` suite against three transports (memory, HTTP, gRPC). In `local` mode it starts `./service serve` with stderr redirected to `/tmp/pgcqrs-server.log`; in `docked` mode it targets containers on ports 26000/26001. Today:

- The EXIT trap unconditionally sends SIGQUIT (`kill -3`) and cats the resulting goroutine dump to console — even when every transport passed (measured: 66% of a passing CI step log was stack trace).
- Test output goes to `/tmp/pgcqrs-test-{memory,http,grpc}.out`, cat'd only on failure.
- Startup readiness is a blind `sleep 1`.
- CI uploads artifacts by globbing `/tmp/pgcqrs-goroutines-*.txt` in `main.yaml` only; `pr.yaml` has no upload step. A hang that trips the job-level 5-minute timeout marks the job *cancelled*, so `if: failure()` steps never run and no artifact is produced — precisely the stuck-service case.
- The service already exposes `GET /ops/liveness` and `GET /ops/readiness` (internal/service/service.go:37-39), probed by the Helm chart (deploy/pgcqrs/templates/deployment.yaml:58-65). Both currently return hardcoded `{ok:true}`, but the service connects to Postgres before binding listeners, so a 200 transitively means "connected and serving."

## Goals / Non-Goals

**Goals:**
- One deterministic diagnostics directory per run, valid identically locally and in CI
- Console shows what ran and what passed; diagnostics never flood it
- Script always self-exits well before any external timeout
- Reuse existing readiness machinery rather than inventing a new probe
- Self-describing artifacts (a downloaded zip explains its own context)

**Non-Goals:**
- Making `/ops/readiness` a real DB-health check (existing TODO stays)
- Adding `grpc.health.v1.Health` to the gRPC service
- Adding a `net/http/pprof` route or other product-code changes (future work; would enable non-destructive stack capture everywhere)
- Changing test content, timeouts of individual suites, or `dev.sh`
- Running the docked path in CI: both workflows invoke the script in `local` mode today (Postgres via raw `docker run`, service built natively), so CI artifacts contain local-mode files (`server.log`, `goroutines.txt`) and the docked capture path is exercised only by manual verification. Adding Docker-based docked execution to CI is deferred future work.

## Decisions

### Diagnostics directory: `run/test-diagnostics/<run-id>/`
- `<run-id>` = UTC timestamp + mode + PID, e.g. `20260823-141505-local-4711`. Second-granularity timestamps alone can collide when runs are scripted back-to-back, and macOS/BSD `date` lacks `%N`, so the PID suffix makes the no-clobber guarantee portable. The base directory anchors to the repository root (git toplevel, falling back to the script's own directory) rather than `$PWD`, so invocation CWD doesn't matter.
- `run/` is gitignored with a root anchor (`/run/`) so only the repository-root directory matches. Chosen over `/tmp` for discoverability ("a file we can look at") and over repo root for cleanliness. Env override `PGCQRS_TEST_DIAG_DIR` replaces the whole base path if needed.
- Files are mode-scoped: each executed suite writes its `test-<transport>.out` (a full run produces all three) and every run gets `summary.txt`; local runs add `server.log` (stderr streamed live — survives hard kills; stderr-only by decision (2026-08-23): stream separation keeps provenance evident, slog emits to stderr so nothing normal is lost, and unexpected stdout surfaces visibly on the console where its anomaly is itself diagnostic — stdout is not redirected anywhere) and `goroutines.txt` on failure; docked runs add `docker-service.log` on failure. Startup failures legitimately precede all suites, so early-failed runs carry fewer files.
- Alternative considered: overwrite-in-place single dir. Rejected: loses prior-run evidence when investigating an intermittent failure after a re-run.

### Console policy
- No `set -x`. Phase lines like `[memory] PASS 1s` / `[grpc] FAIL 4s` — durations measured with `date +%s` (whole seconds) for macOS bash 3.2 portability (`$EPOCHREALTIME` unavailable there, BSD `date` lacks `%N`). The script as a whole restricts itself to bash-3.2-compatible features (no `declare -A`, `mapfile`, `${var,,}`, `&>>` — macOS `/bin/bash` is 3.2).
- Shared phase runner MUST reproduce today's per-suite environment exactly: memory sets `PGCQRS_TEST_TRANSPORT=memory`, HTTP *unsets* it, gRPC sets `grpc`. Unset already defaults to HTTP in all three systest harnesses (`harness_test.go`, `meta/`, `batchr2/`), but preserving unset-vs-set semantics protects against harnesses branching on env presence via `LookupEnv`.
- On failure: print last 40 lines of that transport's output plus the file path. Full text lives in the file/artifact.
- On success: one closing line naming the diagnostics dir. Nothing else.
- Goroutine dump is written to file only; never printed.

### Readiness gate (both modes)
- Poll `GET /ops/readiness` every 250ms up to a 15s deadline before running transports, treating only a literal HTTP 200 as ready (`curl -fsS --max-time 1`; connection success alone would bless a 503, and an unbounded connect could burn seconds of the deadline in one attempt). Local mode derives the target from `${PGCQRS_LISTENER_ADDRESS:-localhost:9000}`, mirroring the service's own resolution (internal/service/config.go:42) so a developer-level override cannot desync gate and listener; docked mode targets the fixed mapping `http://localhost:26000`. The same mirroring covers the transport targets: `HTTP_URL` reuses the readiness target and `GRPC_URL` derives from `${PGCQRS_GRPC_LISTENER_ADDRESS:-localhost:9001}` (internal/service/config.go:59) with a wildcard host (`0.0.0.0`) normalized to `127.0.0.1`, so an override cannot desync gate and suites either — one run must hold exactly one belief about where the service lives. Docked mode hardcodes its URLs because the compose port mapping is the contract there.
- Timeout in local mode → record startup failure, print server-log pointer, exit non-zero; the EXIT trap's non-zero-entry path delivers the SIGQUIT dump (a stuck-mid-startup process is prime dump material) as part of teardown. Timeout in docked mode → record startup failure and exit non-zero (no process ownership).
- Honest semantics: a 200 currently proves only that the HTTP listener is bound — `pgxpool.New` connects lazily (service.go:257), the suture supervisor starts services asynchronously (service.go:278), and the gRPC listener binds without touching Postgres (grpc.go:296). The gate therefore verifies startup, not database health; the failing transports supply the deeper evidence. When `/ops/readiness` later gains a real DB check (explicit non-goal), the script changes nothing: it polls until 200 either way, and its diagnostics remain correct.
- Local-mode race guard: the poll loop also checks `kill -0 $SERVER_PID` each iteration. If the owned process dies mid-poll (e.g., bind failure against a port held by a stray prior instance that answers 200 itself), the script fails immediately with a `server.log` pointer instead of blessing tests against the wrong binary.
- Rationale for reuse: identical endpoint the Helm chart/k8s probes before routing traffic. Same gate in both modes keeps behavior consistent.

### Docked failure-path diagnostics
- On any failure in `docked` mode — transport failure or startup/readiness timeout — copy container logs unconditionally. Resolve the service container via a Docker label filter, `docker ps -aq --filter label=com.docker.compose.service=pgcqrs` (covers stopped containers, i.e., the crash/OOM case), and check `.State.Running` via `docker inspect` before signaling. If running, deliver SIGQUIT via `docker kill --signal=QUIT <id>` (daemon-side signal delivery — the image is `FROM scratch` with no shell or coreutils) and wait briefly for the runtime dump to flush; if the container has already exited there is nothing to signal (no dump obtainable) and the captured logs preserve the crash output instead. Signal failure is never an error. Then `docker logs --timestamps <id> > <diag>/docker-service.log`.
- Resolution deliberately avoids Compose entirely: `dev.sh` invokes the hyphenated `docker-compose` binary with an explicit `--project-name pgcqrs`, so compose-based resolution (`docker compose ps -q pgcqrs`) breaks twice — on v1-only hosts (CLI variant mismatch) and in clones whose directory name differs from `pgcqrs` (project-name mismatch). Either failure silently skips capture AND leaves the SIGQUIT'd container dead, violating the restore guarantee invisibly.
- Multiple label matches are possible because the filter ignores project name *by design* (that is its robustness property): interrupted recreates orphan old labeled containers, restart give-up leaves a stopped-but-labeled container, and a second checkout running docked mode yields another project's labeled container. Container selection among matches (settled 2026-08-23): inspect each candidate (`docker inspect` → `.State.Running`, `.Created`), prefer running containers, break ties by newest `.Created`. If more than one running match exists, proceed with the newest but print one console warning and list every matched ID in `summary.txt` so the guess is visible. Zero matches → skip capture entirely, record `no service container found` in `summary.txt`. Rationale per sub-decision: signaling targets the chosen container only — SIGQUIT dump-and-exit is irreversible, so precision matters most there; log capture stays singular to the chosen container — stale siblings' logs are noise from older runs and one file preserves the spec contract; newest-wins beats refusing to choose — refusal deletes diagnostics exactly in messy environments, and a warned guess beats silence during an incident; absent-container is a note, not a second failure mode — the run already failed for its own reasons. Rejected alternative: signal/capture/restore ALL matches — maximal evidence, but destructive signaling bounces healthy containers from unrelated checkouts and plural log files break the singular contract. Divergent cases require interrupted recreates or concurrent docked stacks, so they are rare; this is determinism insurance, not a hot path.
- Docker ignores `restart: always` after a manual kill (verified experimentally), so the flow MUST finish by restoring the container via `docker start <id>` (works after manual kills, preserves original config, project-name-independent). Restore is strictly best-effort: on failure print one console warning and record `container restore: FAILED` in `summary.txt`; never alter the run's exit code — the failure/cancellation artifact upload depends on that fidelity.
- Console parity: docked failures print the same tail-and-pointer pattern as local failures; captured logs go to file only.
- Deferred alternative noted for future work: a `net/http/pprof` route would make stack capture non-destructive and repeatable across all environments (local/docked/k8s) at the cost of a product-code change and an exposure-surface decision.

### Quiet shutdown on success, dump on failure
- Trap discipline (2026-08-23 second review): the EXIT trap captures `$?` at entry and immediately disables `set -e`; every teardown command is guarded and the trap re-exits with the captured status. Rationale: under `set -e`, a failing command inside the trap *replaces* the script's verdict — `wait` after a signal-death returns 143 and would flip an all-green run to red, and a failed extraction step could mask a genuine FAIL exit. The dump rule keys off the captured status (non-zero ⇒ dump path), which needs no abnormality flag: transport failures, readiness timeout, INT (`exit 130`), and TERM (`exit 143`) all arrive non-zero; success arrives 0. The EXIT trap is the single owner of service signaling and dump extraction — no other code path signals the service, removing the legacy double-dump hazard between phase runner and trap.
- All pass: plain `kill` (TERM), then the same bounded poll-for-death + SIGKILL escalation as the failure path. No SIGQUIT, no dump (nothing to debug). An unbounded success-path `wait` would violate the self-bounding goal: a service hung in SIGTERM handling trips the job timeout, the job is marked cancelled, and no upload step fires — precisely the failure mode this change removes.
- Any failure/hang (non-zero trap entry): SIGQUIT dump, wait for process death (poll `kill -0`, cap 2s) instead of fixed `sleep 0.5`; escalate to SIGKILL if the process survives the wait so no orphan survives any path.
- `goroutines.txt` is produced post-mortem, not live: extract `server.log` from the runtime's stable `SIGQUIT: quit` marker onward (`awk '/^SIGQUIT: quit$/ {on=1} on'`); when the marker is absent, fall back to the tail of `server.log` (~200 lines) prefixed with a `# no SIGQUIT marker found; tail of server.log` comment so the file is never silently empty and always self-describing. Rejected alternative: a `tee | awk` pipeline interposed on stderr captures the dump live and would survive an external SIGKILL during the ~2s teardown window — but a dying tee kills the service itself (Go re-raises SIGPIPE for writes to fd 2), costs two extra processes on every run, and leaves an always-present empty `goroutines.txt` that breaks absence-means-no-dump semantics. Poor trade for such a narrow window.
- Signal chaining: add `trap 'exit 130' INT` and `trap 'exit 143' TERM` alongside the EXIT trap. Bash runs EXIT traps only on normal exit; without chaining, Ctrl-C or CI cancellation skips bounded shutdown and the dump entirely (the streamed `server.log` still survives either way).
- Docked mode has no owned process; its failure path uses the daemon-side container capture described above.

### Self-bounding budget
readiness ≤15s + 3×(go test --timeout 5s) + cleanup ≈ 32s worst case (docked failure paths add ~5s for signal-wait and container restore), far under the 300s job safety net — figures assume `-count 1`; `INTEGRATION_RUN_COUNT` scales suite time linearly. The script therefore always exits on its own, so `if: failure() || cancelled()` artifact upload fires reliably.

### CI wiring
- Both workflows upload via `actions/upload-artifact@v7` (verified current latest major, v7.0.1; workflows previously pinned @v4) with `path: run/test-diagnostics/`, `if: failure() || cancelled()`, `if-no-files-found: warn` (a failure before the diagnostics dir exists must not add upload errors), `retention-days: 30`, artifact name suffixed with the Go matrix version. Cancellation is included deliberately (2026-08-23 second review): plain `failure()` steps are skipped when a job is cancelled, so a user-cancelled or externally-timed-out run would again lose everything even though streamed evidence survives on disk — `cancelled()` closes that gap at zero success-path cost.
- Deletes the `/tmp` glob hack and its apologetic comments in `main.yaml`.

### Run summary (`summary.txt`)
Mode, timestamp, git SHA, Go version, per-phase result + duration, final verdict. Written incrementally where practical so partial runs still explain themselves.

## Risks / Trade-offs

- [Readiness endpoint returns 200 but service is broken later] → Out of scope by design: tests themselves are the deeper check; readiness only gates startup.
- [Timestamped dirs accumulate] → Gitignored; document cleanup (`rm -rf run/`) in operations.md. Sizes are small (tens of KB per run).
- [SIGQUIT dump may truncate if runtime flushes slowly] → Poll process death up to ~2s instead of fixed 0.5s sleep; residual risk acceptable (dump is best-effort evidence, server.log is authoritative).
- [Docked capture leaves container exited] → Verified experimentally: Docker ignores `restart: always` after `docker kill`, so the docked failure path MUST restore the container after capturing logs via `docker start <id>` (best-effort; outcome recorded in summary.txt). Signal-wait is capped (~2s poll) so the path stays bounded.
- [Docked capture path never runs in CI] → Accepted: CI executes local mode only; correctness of the docked flow rests on manual verification (task 8.4) until Docker-in-CI lands.
- [Artifact storage cost on failure/cancellation-only uploads] → Negligible; failures are rare and archives are small.
